# RealSense RGB-D 코스트맵 앱의 실제 병목과 최적화

> 실험일: 2026-11-01 · Jetson Orin Nano Super · RealSense D435 · Fast-SCNN + 2D Costmap  
> 실험 대상: `camera/D435_Fusion_v3.5`

## 1. 가장 중요한 결과

**모델 추론은 충분히 빨랐지만, 실제 카메라 앱은 빠르지 않았습니다.** TensorRT INT8 엔진을 단독으로 측정하면 순수 추론에 약 3 ms가 걸렸지만, 교체 전 앱은 프레임 하나를 처리하는 데 약 **522 ms**가 걸려 **1.87 fps**만 처리했습니다. 카메라 입력이 약 14.8 fps로 들어오는 동안 프레임의 87.4%가 처리되지 못했습니다.

원인을 단계별로 측정하니 시간이 대부분 **GPU 추론 이후의 CPU 작업**에 있었습니다. 깊이 영상을 3D 점으로 변환하고 바닥 평면을 구하는 데 약 211 ms, 코스트맵을 만드는 데 약 268 ms가 걸렸습니다. 이 상태에서 FP32 엔진을 INT8로 바꿔도 앱 전체 처리시간이 거의 변하지 않은 이유입니다.

화면 갱신과 카메라 폴링 방식을 조정하고, 중복 계산을 묶고, softmax·argmax를 GPU 엔진으로 옮긴 결과는 다음과 같습니다.

| 지표 | 변경 전(INT8 엔진 사용) | 3차 최적화 후 | 변화 |
|---|---:|---:|---:|
| 전체 앱 처리속도 | 1.87 fps | **3.47 fps** | 약 86% 증가 |
| 프레임당 처리시간 p50 | 521.6 ms | **284.4 ms** | 약 45% 감소 |
| 입력 프레임 대기 나이 p50 | 267.3 ms | **115.8 ms** | 감소 |
| 카메라 수신부터 처리 완료까지 p50 | 555.2 ms | **320.6 ms** | 감소 |
| 입력 프레임 드롭 비율 | 87.4% | **76.7%** | 10.7%p 감소 |

저장한 동일 캡처 20장의 출력을 비교했을 때, 최적화 과정에서 확인한 점유 격자·비용·자유공간 근거·점 분류·바닥 평면은 비교 기준과 일치했습니다. 그러나 **목표 15 fps(프레임 간격 66.7 ms)에는 도달하지 못했습니다.** 따라서 다음 성능 향상은 코스트맵 알고리즘과 계산량을 조정하는 문제로 남아 있습니다.

## 2. 왜 '엔진만 빠른 것'으로는 부족했나

앱은 대략 **카메라 RGB-D 수신 → Fast-SCNN 분할 → 깊이의 3D 변환 및 바닥 평면 추정 → 코스트맵 생성 → 화면 표시** 순서로 동작합니다. 그중 엔진 벤치마크는 Fast-SCNN 관련 일부만 측정합니다. 카메라 수신, 3D 점 처리, 격자 계산, 스레드 대기는 포함하지 않습니다.

실제 시간의 대부분이 GPU 바깥에 있었기 때문에, FP32와 INT8 추론의 차이 약 3~4 ms를 줄여도 약 522 ms의 전체 처리시간에서는 개선 폭이 작았습니다. **최적화 대상을 정하려면 추론시간과 실제 앱 처리시간을 따로 측정해야 한다는 사실**을 이 실험에서 확인했습니다.

또한 작업 스레드만 따로 실행하면 271 ms였지만, 카메라와 UI가 동시에 작동하는 실제 앱에서는 522 ms였습니다. 동일한 프레임의 계산 자체와 별개로 **다른 스레드와 CPU·Python 실행 자원을 공유하는 비용**이 크게 나타났습니다. 이후 화면 갱신 횟수와 폴링 간격을 줄여 그 경합을 낮췄습니다.

## 3. 어떤 조건에서 측정했나

- **보드**: Jetson Orin Nano Developer Kit Super, L4T R39.2.1, 25W 모드. `jetson_clocks`로 클럭을 고정하고 GPU Min=Max=918 MHz를 각 실행에서 확인했습니다.
- **카메라**: RealSense D435, 펌웨어 5.17.3.10, USB 2.1, 640×480 RGB+Depth, 15 fps. 정지된 실내 장면에서 유효 깊이는 약 72%, 프레임당 약 22.2만 점이었습니다.
- **실행 방식**: 실제 GTK 창을 그리는 `xvfb-run` 가상 디스플레이에서 180초씩 앱을 구동했습니다. 처음 10프레임은 집계에서 제외했습니다. 15 fps의 프레임 마감은 66.7 ms입니다.
- **소프트웨어·코드**: Python 3.12.3, NumPy 1.26.4, OpenCV 4.8.0(cv2 스레드 2), TensorRT 10.16.2.10, pyrealsense2 2.59.1, git `01b58bf` 위에 이 측정·최적화·GPU 디코드·문서 커밋 4개를 올린 상태.
- **전력**: `eval/tegrastats_log.sh`로 1초 간격 기록. 대기 기준선은 6.21 W, RAM 3369 MB, 온도 49.4°C였습니다. 측정 파일은 `results/app_live_1101/<실행>/`입니다.

여기서 **처리시간**은 작업 스레드의 `process()` 구간, **입력 나이**는 카메라 캡처를 받은 뒤 처리를 시작할 때까지의 시간, **끝까지 지연**은 캡처 수신에서 처리 완료까지의 시간입니다. **드롭**은 처리 중 더 새 캡처가 도착해 대기열에서 이전 프레임이 교체된 경우입니다. 서로 다른 개념이므로 같은 '지연'으로 합치지 않았습니다.

### 4-1. 1차: 화면 갱신과 바닥 계산 비용 줄이기

처음에는 새로운 결과가 없어도 UI가 루프마다 약 40 Hz로 화면을 갱신했습니다. 이 동작을 **새 결과·새 캡처·상태 변화가 있을 때만, 최대 10 Hz**로 변경했습니다. 바닥 RANSAC의 반복적인 외적 계산을 묶고, 깊이 지지 검사는 후보의 경계 상자 내부로 제한했습니다.

그 결과 앱 처리 p50은 **522→349 ms**, 실제 처리속도는 **1.87→2.80 fps**로 개선됐습니다. 특히 깊이→3D·바닥 구간이 약 211→78 ms로 줄었습니다. 오프라인 처리에서는 같은 구간이 67→57 ms로 줄었으므로, 라이브에서의 큰 개선에는 화면·카메라 스레드와 작업 스레드 간 경합 감소도 크게 작용한 것으로 해석했습니다.

### 4-2. 2차: 반복 루프와 카메라 폴링 비용 줄이기

카메라 폴링 대기 간격을 3→10 ms로 늘리고 렌더 상한을 5 Hz로 낮췄습니다. 또한 깊이 지지 검사를 슬라이스 기반 배열 연산으로 바꾸고, 자유공간 투영과 가시성 검사에서 표본 위치를 묶어 계산했습니다. 2차원 fancy indexing이 사용된 부분은 평면 인덱스 연산으로 바꿨습니다.

그 결과 처리 p50은 **349→298 ms**, 처리속도는 **2.80→3.30 fps**가 됐습니다. 이 작업은 검사 규칙이나 표본 수를 바꾸는 것이 아니라 같은 값을 계산하는 방식을 바꾼 최적화입니다.

### 4-3. 3차: CPU의 softmax·argmax를 GPU로 이동

Fast-SCNN 추론 후 CPU에서 실행하던 softmax 신뢰도 계산과 argmax를 TensorRT 그래프 내부로 옮겼습니다(`deploy.add_decode`, 매니페스트 `decode_in_graph`). CPU 디코드 약 15 ms가 GPU 쪽으로 이동했고, GPU 디코드의 라벨·신뢰도 결과는 기존 CPU 디코드와 기록상 일치했습니다(`confidence_agreement.md`).

앱 처리 p50은 **298→284 ms**, RAM 증가량은 **422→254 MB**가 됐습니다. 3차 당시 시험 엔진은 `fast_scnn_qat_decode_int8.engine`이었습니다. **이후 15:50에는 실제 앱의 최종 엔진을 PTQ 디코드 엔진으로 교체했습니다.** 둘을 같은 엔진으로 표기하지 않았습니다.

3차 측정에서 UI `render()`의 벽시계 시간이 10.9→58.8 ms로 늘어난 로그도 남았습니다. 렌더 함수의 측정치는 UI 스레드의 대기 시간을 포함합니다. 따라서 이 수치를 곧바로 화면 렌더 연산 자체가 다섯 배 느려졌다는 뜻으로 보기는 어렵습니다. 정확한 발생 원인은 별도로 분리 측정하지 않았습니다.

### 출력은 그대로 유지됐나

`eval.app_profile --compare`는 동일 캡처에서 점유 격자(`physical`), 비용(`cost`), 자유공간 근거(`free_evidence`), 점 분류(`point_classes`), 바닥 평면(`normal`, `offset`, `ok`)을 비교합니다. 라운드 1·2는 저장 캡처 **20/20프레임에서 차이 0셀**로 기록됐으며, 3차 GPU 디코드 후 오프라인 비교도 20/20프레임 일치했습니다.

계산 순서와 묶음을 바꾸되 표본 수를 줄이거나 좌표 정밀도를 낮추는 변경은 넣지 않았습니다. 따라서 **이 단계의 최적화 결과는 출력 동일성 검증을 동반한 결과**입니다. 뒤에서 다루는 격자 해상도 변경은 출력이 달라지는 별도 실험입니다.

## 7. 격자 크기를 키우면 속도와 지도는 어떻게 달라지나

현재 코스트맵 격자 해상도는 **5 cm**입니다. 이를 **10 cm**로 변경하면 같은 면적을 표현하는 셀 수가 14,400개에서 3,600개로 4분의 1이 됩니다. 격자 관련 연산량을 줄이기 위한 실험이지만, 장애물 표현과 통로 폭에도 영향을 줍니다.

| 코스트맵 단계 / 후보 검토 | 151.7 / 55.0 | 104.8 / 46.8 |
| 깊이→3D·바닥 (점 단계, 불변) | 53.7 | 54.0 |
| 지도 면적 m² (3장 평균): 자유 / 장애물 / 팽창 띠 / 미확인 | 3.14 / 3.52 / 1.05 / 29.35 | 3.25 / 5.15 / 1.31 / 27.60 |

오프라인 처리 p50은 **228.5→181.7 ms(약 20% 감소)**로 개선됐습니다. 그러나 지도에서 장애물 면적은 평균 **3.52→5.15 m²(약 45% 증가)**로 바뀌었습니다. 얇은 장애물이 10 cm 셀을 차지하면서 장애물 표현이 두꺼워진 결과입니다.

로봇 너비 0.4 m에 따른 금지 반경 0.25 m와 팽창 반경 0.40 m는 미터 단위를 유지하므로 설정 자체는 변하지 않습니다. 다만 실제 격자 표현은 5 cm보다 거칠어져 좁은 통로를 더 많이 막을 수 있습니다. 이 실험 기록에서는 **5 cm 격자의 약 60 cm 통로가 10 cm에서는 약 70 cm로 제한될 수 있다**고 정리했습니다.

따라서 10 cm 설정은 **처리속도만 보고 채택할 변경이 아닙니다.** 시연 동선의 최소 통과 폭이 약 70 cm 이상인지 확인한 뒤 선택해야 합니다. 원본 이미지와 비교 로그는 `results/app_profile_1101/res010/`, `results/app_profile_1101/res_compare/`에 있습니다.

## 7-1. 깊이 점을 솎아내면(데시메이션 2×2) 어떻게 달라지나

점 단계의 계산량을 줄이기 위해 `depth.decimation` 설정을 추가했습니다(기본값 1 = 끔). 값이 2이면 깊이 영상을 2×2 블록마다 **사용 깊이가 있는 가장 가까운 픽셀 하나**로 줄이고, 내부 파라미터도 함께 줄입니다. 지지 검사·후보 검토·가시성 검사가 픽셀 이웃 관계를 쓰기 때문에 점만 솎아낼 수는 없고, 해상도가 낮은 카메라처럼 영상 자체를 줄여야 이후 단계가 그대로 성립합니다. 기본값 1에서는 출력이 변경 전과 20/20 프레임 동일했습니다(`results/app_profile_1101/dec1`).

| | 5 cm, 데시메이션 없음 | 데시메이션 2 (+픽셀 기준값 비례 조정) |
|---|---|---|
| 점 수 | 22.2만 | 5.8만 |
| 오프라인 처리 p50 ms | 228.5 | 139.9 (−39%) |
| 깊이→3D·바닥 / 코스트맵 (후보 검토) / 마무리 | 53.7 / 151.7 (55.0) / 12.6 | 38.3 / 87.8 (25.0) / 3.7 |
| 점유 격자가 달라진 셀 (20장) | 기준 | 4.2% |
| 장애물 셀 사라짐 / 새로 생김 | | 17.3% / 3.8% (1~2 m 13.8%, 3 m 이상 21.4%) |
| 자유 셀 사라짐 / 새로 생김 | | 15.6% / 8.8% (1~2 m 8.7%, 3 m 이상 18~23%) |

처리시간은 **228.5→139.9 ms(약 39% 감소)**로, 네 가지 후보 중 가장 큰 개선 폭입니다. 그러나 지도 손실도 큽니다. 픽셀 단위 기준값(이웃 지지의 깊이 점프 한계 ×2, 작은 성분 60→15픽셀, 의미 장애물 최소 점 2→1)을 맞춰도 장애물 셀 손실은 22%에서 17%로만 줄었습니다. 지지 검사 탈락이나 후보 보류가 늘어서가 아니라(둘 다 오히려 줄었습니다), **점이 1~3개뿐이던 셀이 점을 아예 받지 못해서**입니다. 5 cm 셀이 깊이 픽셀 몇 개로만 보이는 먼 거리, 비스듬한 바닥, 물체 윤곽에서 그렇습니다.

차이 그림(`results/app_profile_1101/res_compare/diff_dec2b_frame*.png`, 파랑 = 사라진 장애물, 주황 = 사라진 자유)을 보면 물체가 통째로 빠지지는 않고 윤곽이 한 셀씩 깎이며, 자유 복도 안에 작은 구멍이 생깁니다. 윤곽 한 셀은 팽창 띠가 흡수하지만, 자유공간의 구멍은 계획기에 '미확인' 칸이 되어 지나가지 못하는 자리가 됩니다.

**판단: 이대로 켜지 않았습니다.** 살릴 길은 '가까운 곳만 솎기'입니다. 셀당 픽셀 수는 거리 제곱에 반비례하므로(1 m 약 400개, 2 m 100개, 4 m 25개) 2.5 m 안쪽만 2×2로 솎으면 셀이 점을 잃지 않으면서 점 수의 대부분이 줄어듭니다. 다만 지지 검사와 후보 검토가 픽셀 이웃 관계를 쓰므로 가까운 격자와 먼 격자를 나눠 처리하는 구조 변경이 필요합니다(하루 정도). 원본은 `results/app_profile_1101/dec2`, `dec2b`입니다.

## 8. 15 fps에 도달하려면 무엇을 바꿔야 하나

현재 라이브 p50이 284 ms인 반면, 목표 15 fps의 시간 예산은 **66.7 ms**입니다. 동일한 출력 규칙을 유지하는 배열·루프 최적화만으로 남은 차이를 없애기는 어렵습니다. 다음 선택은 **연산량을 줄이거나 계산 경로를 바꾸는 설계 변경**이므로, 속도와 지도 품질을 함께 측정해야 합니다.

| 검토 항목 | 현재 계산에서 줄이려는 부분 | 확인해야 할 대가·조건 |
|---|---|---|
| 깊이 점 2×2 데시메이션 | 약 22만 점 → 약 5.8만 점 | 오프라인 약 89 ms 개선 실측(7-1절). 장애물 셀 17%·자유 셀 16% 손실로 그대로는 채택하지 않음. '가까운 곳만' 변형 필요 |
| 격자 10 cm | 14,400 셀 → 3,600 셀 | 오프라인 약 47 ms 개선 실측. 장애물 면적 증가·통로 폭 축소 |
| 셀당 투영 표본 축소/시야 내 셀만 계산 | 셀 × 표본 5 × 높이 9 계산 | 가시성·자유공간 검증 결과가 달라질 수 있음 |
| 후보 검토의 반복·표본·후보 수 제한 | `local_floor_model`, `MotionGuard` | 이동·장애물 판단 규칙에 영향 가능 |
| 카메라 정렬 위치 변경 | `rs.align`과 프레임 수명 관리 | 스레드 경합을 줄일 수 있지만 SDK frameset을 유지하는 구조 변경 필요 |
| GPU 또는 C++로 격자 계산 이전 | CPU의 점 투영·격자 검사 | 구현 비용과 결과 검증 필요 |

격자 10 cm(−47 ms)와 점 데시메이션(−89 ms)을 각각 실측했지만, **함께 적용한 실측값은 없으며** 둘 다 지도 출력이 달라지는 변경입니다. 실제 채택은 **변경 → 동일 캡처 오프라인 평가(시간·지도 차이) → 카메라 180초 평가(fps·드롭·지연)** 순으로 판단해야 합니다.

## 9. 실제 앱에 적용한 최종 모델과 실행 조건

### 9-1. 15:50 — 최종 PTQ 디코드 엔진 채택

앞의 최적화 실험에서는 Q/DQ 기반 GPU 디코드 엔진도 사용했지만, 최종 앱에는 **`models/logits/fast_scnn_decode_int8.engine`**이 적용됐습니다. 이 엔진은 로짓 ONNX에 `deploy.add_decode`를 적용하고 TensorRT 엔트로피 102장으로 PTQ한 것입니다.

동일한 프로파일 조건에서 PTQ 디코드 엔진은 **2.057 ms**, Q/DQ 디코드 엔진은 **2.074 ms**였습니다. FP32 대비 클래스 일치율은 두 엔진 모두 99.41%, 두 엔진끼리 99.94%였습니다. 성능이 비슷한 조건에서 **생성 경로가 단순한 PTQ 엔진**을 선택한 것입니다. 원본은 `results/confidence_agreement_1101_ptq_b/`입니다.

빌드 과정에서도 확인한 문제가 있었습니다. 다른 앱 프로세스가 CPU 4코어를 사용 중이던 15:32 첫 빌드에서는 TensorRT가 Conv 41개 중 36개를 FP16으로 선택했고, 실행시간이 2.69 ms였습니다. 보드가 유휴 상태가 된 뒤 `models/timing.cache`를 사용해 재빌드하자 INT8 48층, 2.06 ms로 바뀌었습니다. **동일 모델이라도 엔진 빌드 당시의 보드 부하가 자동 튜닝 결과에 영향을 줄 수 있으므로, 빌드 뒤 실제 레이어 정밀도 구성을 확인해야 합니다.**

### 9-2. SSH로 화면을 볼 때 느렸던 이유 분리

15:29~15:45의 `ssh -X` GUI 세션은 클럭 고정·가상 디스플레이 세션보다 훨씬 느렸습니다. 처음 2분 기준 처리 p50은 541 ms, 처리속도는 1.83 fps였고 바닥 검출 성공률은 99.6%였습니다. 원인을 구분하기 위해 **가상 디스플레이에서 클럭 고정만 해제한 180초 실험**을 별도로 수행했습니다.

| | 클럭 고정 (라운드 3) | 클럭 미고정 | 사용자 ssh -X 세션 (미고정, 처음 2분) |
|---|---|---|---|
| 처리 fps | 3.47 | 3.10 | 1.83 |
| 처리 ms p50 / p95 | 284 / 339 | 317 / 368 | 541 / 729 |
| SCNN 단계 (모델 실행) | 10.2 (3.8) | 15.1 (8.1) | 15.2 |
| 깊이→3D·바닥 / 코스트맵 | 63 / 189 | 69 / 206 | 275 / 234 |
| 화면 그리기 p50 | 58.8 | 9.2 | 94.1 |
| 입력 나이 / 지연 p50 | 116 / 321 | 132 / 357 | 327 / 578 |
| 보드 전력 W | 8.43 | 6.37 | (기록 없음) |
| GPU 클럭 | 918 고정 | 306 (사용률 2% 라 올라가지 않음) | 미고정 |

클럭을 해제하니 처리속도는 3.47→3.10 fps(약 12% 감소)가 됐습니다. GPU 사용률이 낮아 GPU 클럭이 약 306 MHz에 머물며 모델 실행도 3.8→8.1 ms로 늘었습니다. 하지만 **3.10→1.83 fps**라는 추가 하락을 클럭만으로 설명할 수는 없습니다.

`ssh -X`에서는 화면 전달과 암호화 등 UI 경로가 달라지므로 추가 비용의 후보로 봤습니다. 렌더 시간도 94 ms까지 기록됐지만, **이 원인을 따로 떼어 실측한 것은 아닙니다.** 따라서 사용자 GUI 세션 수치를 모델 또는 알고리즘 단독 성능으로 판단하지 않았습니다.

시연에서는 Jetson에 모니터를 직접 연결한 환경을 우선하고, 성능을 비교할 때는 같은 전력 모드·클럭·화면 조건을 맞추는 것이 이 실험의 결론입니다. `view.live_render_max_hz`는 5로 두었고, 미리보기가 끊겨 보이면 10까지 올리는 것을 권합니다(처리 fps 약 0.3 감소).

## 11. 남은 결론

**이번에 해결한 것은 '모델이 느리다'는 문제가 아니라 'GPU 모델 밖에서 시간이 쓰이는 위치를 찾아 줄이는 문제'입니다.** 앱 처리속도는 1.87→3.47 fps로 개선됐고, 저장 캡처 20장 기준 출력 일치성도 확인했습니다. 그러나 15 fps에는 아직 미치지 못하며, 다음 단계에서 필요한 것은 **점 수·격자·검증 표본을 어떻게 줄일지에 대한 팀의 설계 결정과 지도 품질 재검증**입니다.
