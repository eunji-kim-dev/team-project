# Fast-SCNN TensorRT 정밀도별 성능 비교

> 최종 비교: 2026-10-30 19:57 · Jetson Orin Nano Super · 25W · 클럭 고정  
> 평가 데이터: 검증 영상 26장, 640×480 · 반복 5회

## 1. 무엇을 비교했고, 무엇을 확인했나

FP32 모델을 기준으로 **FP16과 INT8 변환이 실제 Jetson에서 얼마나 빨라지는지**, 그리고 장애물 분할 결과가 달라지는지를 비교했습니다. 단순히 모델이 빠른지를 보는 것뿐 아니라, 장애물을 바닥으로 잘못 분류하는 비율도 함께 확인했습니다. 코스트맵에서는 이 오류가 통과 가능한 공간을 잘못 판단하게 만들기 때문입니다.

최종 측정에서 GPU FP32의 **추론만** 걸리는 시간은 5.80 ms였고, FP16은 3.43 ms, PTQ INT8은 2.96 ms였습니다. 명시적 Q/DQ를 사용한 최종 INT8 엔진도 2.98 ms로 PTQ와 사실상 같았습니다. 한편 mIoU는 모든 모델에서 약 0.931~0.932, 장애물→바닥 오류는 1.65~1.67%로 유지됐습니다.

다만 이 수치는 **모델 전처리·추론·후처리의 벤치마크**입니다. 실제 RGB-D 카메라 앱의 처리 속도를 뜻하지 않습니다. 앱 병목은 `app_pipeline.md`에서 별도로 다룹니다.

### 최종 결과에서 먼저 볼 값

| 모델 | 전체 처리 p50 | 순수 추론 p50 | mIoU | 장애물→바닥 오류 | FP32 대비 출력 일치율 |
|---|---:|---:|---:|---:|---:|
| CPU FP32 (기준) | 37.49 ms | 33.86 ms | 0.932 | 1.67% | 기준 |
| GPU FP32 | 9.30 ms | 5.80 ms | 0.932 | 1.67% | 100.00% |
| FP16 | 6.95 ms | 3.43 ms | 0.932 | 1.67% | 99.99% |
| PTQ INT8 | 6.46 ms | 2.96 ms | 0.931 | 1.65% | 99.41% |
| Q/DQ INT8 (최종) | 6.51 ms | 2.98 ms | 0.931 | 1.65% | 99.41% |

**해석할 때 구분할 지표가 두 가지 있습니다.** mIoU와 장애물→바닥 오류는 *정답 라벨*과 비교한 정확도입니다. 반면 FP32 대비 일치율은 *원래 FP32 모델의 출력*과 얼마나 같은지 보는 변환 충실도입니다. 일치율이 낮다고 반드시 정확도가 낮다는 뜻은 아닙니다.

## 2. 실험 방법

- 보드: NVIDIA Jetson Orin Nano Developer Kit Super, L4T R39.2.1, NV Power Mode 25W, `jetson_clocks` 고정 (시작 시 `--show` 로 GPU 918 MHz, EMC 3199 MHz Min=Max 확인하고 아니면 측정을 시작하지 않음, 끝나면 복원)
- 소프트웨어: CUDA 13.2, TensorRT 10.16.2.10, onnxruntime 1.31.1 (cpu_fp32 전용), Python 3.12.3, numpy 1.26.4, OpenCV 4.8.0
- 코드: git `0c5d644` (작업 트리 clean). 도구 `python -m eval.bench_engines`, 일반 터미널에서 실행 (디버거·프로파일러 없음)
- 입력: `data/splits/val.txt` 26장, 640×480 color PNG. 정답지 `data/labels_RGB` (바닥 / 장애물 / 그 외)
- 절차: 모델당 warmup 20프레임 버림 → 26장 × 5회, 회차 사이 30초 쿨다운. p50/p95 는 5회 전체 프레임 기준. 반복 변동% = 회차별 p50 의 (최대−최소)/평균
- 기준 모델(일치율 열): cpu_fp32 = FP32 ONNX 를 onnxruntime CPU 로 같은 세션에서 실행한 결과. mIoU·장애물→바닥% 는 정답지 기준이고, 일치율은 fp32 대비 변환 충실도다. 둘은 다른 지표다

이번 비교에서 사용한 최종 엔진은 다음과 같습니다.

- GPU FP32: `models/fast_scnn_fp32.engine`
- FP16: `models/fast_scnn_fp16.engine`
- PTQ INT8: `models/fast_scnn_int8.engine` (TensorRT 엔트로피 캘리브레이션, `calib_list.txt` 102장)
- 명시적 Q/DQ INT8: `models/calib_trt_adds/fast_scnn_qat_int8.engine` (TensorRT 캐시의 활성화 scale을 사용하고 Conv 입력·가중치 및 잔차·fusion Add 입력에 Q/DQ 적용)

정밀도별 엔진은 모두 같은 보드와 TensorRT 환경에서 생성했습니다. TF32는 끄고 workspace는 2048 MB로 설정했으며, 실제 빌드 옵션은 각 `.engine.json`에 남겼습니다. 원본 데이터는 `results/bench_final_1030b/`에 있습니다.

## 3. Q/DQ 엔진이 처음에는 느렸던 이유

초기 명시적 Q/DQ 엔진의 추론 시간은 3.17 ms로 PTQ의 2.96 ms보다 약 0.2 ms 느렸습니다. 처음에는 QAT 학습 자체의 영향일 수 있었지만, 레이어별 실행을 확인한 결과 **문제는 학습 결과가 아니라 Q/DQ 연산을 삽입한 위치**에 있었습니다.

원래 `quant.py`는 Conv 입력과 가중치만 양자화했습니다. 이때 잔차 연결과 fusion의 Add 입력에는 Q/DQ가 없어, TensorRT가 해당 구간을 INT8로 이어서 처리하지 못했습니다. 그 결과 Add 앞 Conv 12개가 FP16으로 출력됐고, 다음 Conv에 들어가기 전에 FP16→INT8 변환이 추가됐습니다.

이를 해결하기 위해 잔차 블록 6곳과 fusion Add 입력에 필요한 Q/DQ를 추가했습니다. 관련 구현은 `quant.quantize_residual_adds`, `quant.quantize_fusion_add`이며, 이전 배치를 재현할 때는 `--no-quant-adds`를 사용합니다.

### 레이어 프로파일 비교

| | ptq_int8 | qat_int8 (기존) | qat_adds (수정) |
|---|---|---|---|
| INT8 conv | 40층 0.94 | 28층 0.72 | 38층 0.91 |
| FP16 출력 conv | 없음 | 12층 0.25 | 1층 0.03 |
| Reformat (형식 변환) | 7개 0.11 | 20개 0.29 | 11개 0.11 |
| 전체 (프로파일러 없이) | 1.77 | 1.96 | 1.79 |

수정 후 INT8 Conv 구간은 기존 28층에서 38층으로 늘었고, 형식 변환(Reformat)은 20개에서 11개로 줄었습니다. **수정한 Q/DQ 엔진의 순수 추론 p50은 2.98 ms**로, PTQ 2.96 ms와의 속도 차이가 거의 없어졌습니다. FP32 업샘플(0.15 ms)과 argmax(0.33 ms)가 포함된 출력부는 두 엔진 공통 비용으로 남으며 전체의 약 25%입니다.

여기서 `qdq_adds_0iter`는 학습하지 않고 활성화 scale과 Add Q/DQ를 적용한 엔진이고, `qat_adds`는 그 설정을 바탕으로 300 iter 동안 QAT 후보를 만들고 선택 규칙을 적용한 엔진입니다. **이번 최종 채택은 iter 0**입니다. 학습한 후보가 모두 장애물→바닥 오류 허용 기준을 초과했기 때문에(가장 좋은 iter 100도 mIoU 0.9321, 장애물→바닥 1.711%로 기준 1.648%를 넘음), `qat_adds`와 `qdq_adds_0iter`는 결과적으로 동일한 ONNX를 사용합니다(SHA-256 동일). 따라서 최종 표의 Q/DQ INT8 결과를 *QAT 학습으로 얻은 성능 향상*이라고 해석하면 안 됩니다.

수정 전 엔진의 추론 p50 3.17 ms와 수정 후 2.98 ms를 비교하면, 개선의 원인은 Q/DQ 배치 변경으로 정리됩니다. 로짓 출력 엔진 `models/calib_trt_adds/fast_scnn_qat_logits_int8.engine`도 생성했으며, 카메라 앱에서의 신뢰도 판정 비교는 `confidence_agreement.md`에 있습니다.
