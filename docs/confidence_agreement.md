# INT8 전환이 카메라 앱의 실제 판정에 미치는 영향

> 측정일: 2026-11-01 13:51  
> 대상: Fast-SCNN 로짓 출력 · 검증 이미지 26장 · 바닥/장애물/그 외 3개 클래스

## 1. 왜 이 검증이 필요한가

기존 `bench_table.md`의 출력 일치율은 **각 픽셀에서 최종 클래스(argmax)가 같은지**를 측정한 값입니다. 하지만 실제 카메라 앱 `camera/D435_Fusion_v3.5`는 클래스만 보지 않습니다. softmax 신뢰도가 `config.json`에 정한 기준값을 넘는 픽셀만 채택합니다.

따라서 FP32와 INT8이 모두 같은 픽셀을 '바닥'으로 분류하더라도, FP32의 바닥 신뢰도가 0.71이고 INT8의 신뢰도가 0.69라면 **바닥 채택 기준 0.70에서 앱의 판단은 달라집니다.** 이 문서는 그런 변화가 실제로 얼마나 나타나는지, 그리고 그 변화가 정답 기준의 장애물 판정을 나쁘게 만드는지 확인하기 위해 작성했습니다.

## 2. 결과부터 요약

INT8과 FP32의 argmax 클래스 일치율은 **99.41%**였습니다. 그러나 앱의 신뢰도 기준을 적용하면 **기준 모델이 채택했던 픽셀을 분모로 한 판정 뒤집힘 비율**은 항목별로 달랐습니다. 장애물 채택은 0.86%, 바닥 관련 판정은 2.57~3.01%였습니다.

변화의 방향도 확인했습니다. 모든 판정에서 INT8 때문에 *기존 채택이 취소된 픽셀(잃음)*이 *새로 채택된 픽셀(얻음)*보다 많았습니다. 특히 바닥 계열에서 재현율이 0.47~1.33%p 감소했습니다. 하지만 정답 장애물을 바닥으로 잘못 채택하는 비율은 측정상 증가하지 않았습니다. **이 검증에서는 신뢰도 기준값을 조정할 근거가 발견되지 않았습니다.**

중요한 범위 구분이 있습니다. 이것은 **이미지 픽셀과 앱의 신뢰도 판정 마스크**를 비교한 결과이지, 카메라로 생성한 최종 코스트맵 셀까지 직접 비교한 결과는 아닙니다.

## 3. 비교 방법

원본 실험: `python -m eval.confidence_agreement` · `results/confidence_agreement_1101/`.

- 보드는 Jetson Orin Nano Developer Kit Super(L4T R39.2.1), 25W 모드였습니다. 시간 벤치마크가 아니어서 클럭은 고정하지 않았습니다.
- TensorRT 10.16.2.10, ONNX Runtime 1.31.1, PyTorch 2.12.0+cu132, Python 3.12.3, NumPy 1.26.4, OpenCV 4.8.0을 사용했습니다.
- git `e24898f`와 `eval/confidence_agreement.py`를 사용했습니다. 기존 앱 코드는 수정하지 않고 `prepare_input`, `decode_prediction`, `TrtBackend`, `TorchBackend` 등을 불러와 앱과 같은 전처리·후처리 경로를 적용했습니다.
- 입력은 `data/splits/val.txt`의 640×480 이미지 26장(총 약 798.7만 픽셀)이며 정답은 `data/labels_RGB`입니다.
- `fusion.sample_semantics`와 같은 규칙에 따라 픽셀 경계 1px을 제외했습니다(`boundary_erode_px=1`).

### 비교한 실행 경로

| 이름 | 실행 방식 | 파일 |
|---|---|---|
| `cpu_fp32` (기준) | ONNX Runtime CPU FP32, 4 threads | `models/logits/fast_scnn_logits.onnx` |
| `gpu_fp32` | TensorRT GPU FP32 | `models/logits/fast_scnn_logits_fp32.engine` |
| `int8` | TensorRT GPU INT8, 명시적 Q/DQ | `models/calib_trt_adds/fast_scnn_qat_logits_int8.engine` |
| `torch_cpu` | 앱의 PyTorch CPU FP32 | `checkpoints/best_mIoU_iter_1600.pth`에서 추출한 state_dict |

모든 모델의 로짓 출력은 `[1,3,480,640]`이며, 사양 기록은 `models/standard_fastscnn.json`입니다. 기록된 SHA-256 앞 16자리는 각각 `cpu_fp32` e314afd29ea14bea, `gpu_fp32` 4a36b1071afe4390, `int8` cae54eb7c11a1aa8, `torch_cpu` 9c67ad82cb9e1ef6입니다. `TorchBackend`에는 모델의 state_dict만 전달해야 하므로 `deploy.export_onnx.CheckpointLoader`로 별도 추출했습니다.

### 무엇을 '판정이 달라졌다'고 계산했나

앱이 사용하는 판정 마스크는 **해당 클래스 선택 + softmax 신뢰도 기준 통과 + 경계 픽셀 제외**를 동시에 만족하는 픽셀의 집합입니다.

- **전체 픽셀 일치율**: 두 모델의 판정 마스크가 일치하는 픽셀의 비율입니다. 둘 다 '채택 안 함'인 픽셀도 포함되므로 높게 나올 수 있습니다.
- **판정 IoU**: 두 모델이 채택한 픽셀 집합의 교집합/합집합입니다.
- **뒤집힘 비율**: `(FP32에서 채택했으나 INT8에서 잃은 픽셀 + INT8에서 새로 얻은 픽셀) ÷ FP32에서 채택했던 픽셀`입니다.
- **기준 ±0.02 안 비율**: FP32에서 채택된 픽셀 중 신뢰도가 판정 경계 ±0.02에 위치한 픽셀의 비율입니다.
- **정답 기준 평가**: 채택된 픽셀의 정밀도·재현율과 잘못된 공간 판단으로 이어질 수 있는 '위험 누출'을 별도로 계산했습니다. 바닥 판정의 위험 누출은 실제 장애물을 바닥으로 채택한 비율입니다. 장애물·그 외 판정의 위험 누출은 실제 바닥을 해당 클래스로 채택한 비율입니다.

## 4. FP32 실행 경로부터 검증

GPU FP32와 PyTorch CPU 경로를 ONNX Runtime CPU FP32 기준과 비교했습니다. 두 비교 모두 클래스 일치율은 100.00%, 신뢰도 차이는 평균·최대 모두 기록상 0.000, 여섯 판정의 뒤집힘은 0.00%였습니다. 즉 **PyTorch→ONNX→TensorRT FP32 변환 자체는 이번 데이터에서 앱의 판단을 바꾸지 않았습니다.** 따라서 INT8은 동일한 FP32 기준과 비교할 수 있습니다.

## 5. INT8에서 앱의 판정이 얼마나 달라졌나

앱이 사용하는 신뢰도 기준은 바닥 채택 0.70, 장애물·그 외 0.75, 깊이 장애물과 SCNN 바닥 판단 충돌 보류 0.85, 의미적 자유공간 내부 0.90, 자유공간 연속성 0.75입니다.

INT8과 FP32 간 신뢰도 차이의 절댓값은 평균 0.0062, p99 0.120, 최대 0.493이었습니다. 부호를 가진 평균 차이(INT8−FP32)는 −0.0021입니다.

|---|---|---|---|---|---|---|---|---|---|---|
| 바닥 채택 | 바닥 | 0.70 | 99.56 | 0.9746 | 2.57 | 1.58 | 0.99 | 1.10 | −0.0074 | 137.6 |
| 장애물 채택 | 장애물 | 0.75 | 99.41 | 0.9915 | 0.86 | 0.48 | 0.38 | 0.45 | −0.0012 | 555.2 |
| 그 외 채택 | 그 외 | 0.75 | 99.88 | 0.9874 | 1.27 | 0.74 | 0.53 | 0.46 | −0.0046 | 74.3 |
| 깊이 장애물·SCNN 바닥 충돌 보류 | 바닥 | 0.85 | 99.54 | 0.9719 | 2.83 | 2.06 | 0.77 | 2.01 | −0.0062 | 130.1 |

가장 높은 뒤집힘 비율은 신뢰도 기준이 0.90인 **의미적 자유공간 내부 판정(3.01%)**에서 나왔습니다. 기준값 가까이에 위치한 픽셀이 상대적으로 많았기 때문입니다. 모든 항목에서 '잃음'이 '얻음'보다 많아, INT8은 FP32보다 기존 채택 영역을 조금 줄이는 방향으로 작용했습니다.

이 변화는 예컨대 바닥 판정 기준 0.70에서는 뒤집힘 2.57%, 기준 0.85에서는 2.83%, 기준 0.90에서는 3.01%로 나타났습니다. 하지만 **99% 수준의 전체 픽셀 일치율만 보고 이 차이를 무시해서도 안 되고, 뒤집힘 3%를 곧바로 장애물 검출 실패 3%로 읽어서도 안 됩니다.** 다음의 정답 기준 결과로 판단해야 합니다.

## 6. 실제 정답 기준으로는 나빠졌나

| 판정 | 기준 | fp32 재현율% / 정밀도% / 위험 누출% | int8 재현율% / 정밀도% / 위험 누출% | int8 − fp32 (재현율 pp / 누출 pp) |
|---|---|---|---|---|
| 바닥 채택 (바닥) | 0.70 | 90.43 / 96.15 / 0.93 | 89.96 / 96.22 / 0.90 | −0.47 / −0.03 |
| 장애물 채택 (장애물) | 0.75 | 95.98 / 98.97 / 2.43 | 95.88 / 98.98 / 2.44 | −0.10 / +0.01 |
| 그 외 채택 (그 외) | 0.75 | 92.36 / 99.25 / 0.00 | 92.20 / 99.28 / 0.00 | −0.16 / 0.00 |
| 깊이 장애물·SCNN 바닥 충돌 보류 (바닥) | 0.85 | 86.71 / 97.49 / 0.57 | 85.64 / 97.55 / 0.55 | −1.07 / −0.02 |
| 의미적 자유공간 내부 (바닥) | 0.90 | 84.58 / 97.90 / 0.46 | 83.25 / 97.94 / 0.45 | −1.33 / −0.01 |
| 자유공간 연속성 (바닥) | 0.75 | 89.51 / 96.62 / 0.80 | 88.84 / 96.70 / 0.77 | −0.67 / −0.03 |

정답지와 비교하면 바닥 계열의 재현율은 FP32 대비 0.47~1.33%p 줄었지만, 실제 장애물을 바닥으로 채택하는 위험 누출은 0.93→0.90%, 0.57→0.55%, 0.46→0.45%, 0.80→0.77%였습니다. 장애물 채택의 재현율은 95.98→95.88%, 바닥을 장애물로 잘못 채택하는 비율은 2.43→2.44%였습니다.

따라서 **이번 검증 이미지에서는 INT8의 신뢰도 변화가 장애물 오판 증가로 이어지지 않았습니다.** 대신 바닥으로 채택하는 픽셀의 일부가 줄어들었습니다. 원래 앱 기준값을 조정하지 않기로 한 이유가 이것입니다.

사진별 바닥 채택 뒤집힘은 0106 7.65%, 0073 6.41%, 0107 5.30%, 0077 5.08%, 0038 0.59%였습니다. FP32에서 바닥으로 채택한 픽셀이 적은 이미지(예: 0106 약 2.6만 픽셀)일수록 비율이 크게 나올 수 있습니다. 원본은 `results/confidence_agreement_1101/per_image.csv`에 있습니다.

## 7. 실제 앱에 적용한 엔진 변경 이력

### 13:51 — INT8 로짓 엔진의 판정 검증

FP32 로짓 엔진과 INT8 로짓 엔진을 비교했고, 정답 기준의 판정 성능이 유지되는 것을 확인했습니다. 이에 앱 폴더에서 FP32 로짓 엔진을 `fast_scnn_qat_logits_int8.engine`과 매니페스트로 교체했습니다. 설정파일의 신뢰도 기준은 그대로 유지했으며, 모델 로드 READY와 유효한 라벨·신뢰도 출력까지 확인했습니다.

### 14:55 — softmax와 argmax를 GPU 엔진으로 이동

CPU에서 프레임당 약 15 ms 걸리던 `softmax`·`argmax` 후처리를 TensorRT 그래프로 옮겼습니다. `deploy.add_decode`를 사용해 로짓 ONNX 뒤에 `Softmax→ReduceMax(confidence)`와 `ArgMax→Cast(labels)`를 연결했습니다. Q/DQ 디코드 엔진은 `models/calib_trt_adds/fast_scnn_qat_decode_int8.engine`(SHA-256 앞 16자 a2bcc67acc2de136)입니다.

같은 INT8 로짓 엔진과 **CPU에서 디코드한 결과**를 GPU 디코드 결과와 비교했을 때, 클래스 일치율은 100.00%, 신뢰도 차이 최대는 기록상 0.000, 여섯 판정의 뒤집힘은 0픽셀이었습니다. 즉 이 실험에서 GPU 디코드 이동 자체는 판정을 바꾸지 않았습니다.

### 15:50 — 앱의 최종 채택은 PTQ 디코드 엔진

최종적으로는 생성 과정이 더 단순한 **PTQ 엔트로피 기반 디코드 엔진** `models/logits/fast_scnn_decode_int8.engine`을 앱에 사용했습니다. 이 엔진은 FP32 대비 클래스 일치율 99.41%, 평균 신뢰도 차이 0.0062였고, 앞의 Q/DQ 디코드 엔진과는 클래스 99.94% 일치, 평균 신뢰도 차이 0.0007이었습니다. 관련 원본은 `results/confidence_agreement_1101_ptq_b/`, 앱 실행 결과는 `app_pipeline.md`에 있습니다.

**문서 앞부분의 13:51 실험 대상은 Q/DQ 로짓 엔진이고, 최종 앱에 사용된 것은 15:50의 PTQ 디코드 엔진입니다.** 둘의 역할과 시점을 혼동하지 않아야 합니다.

## 8. 결과 해석 범위

이번 검증은 클래스·신뢰도·픽셀 단위 판정까지입니다. 실제 앱은 이후 깊이 샘플링, 평면 검증, 격자 집계를 거칩니다. **최종 코스트맵의 셀 단위 차이는 이 문서에서 직접 측정하지 않았습니다.** 해당 차이를 검증하려면 동일한 저장 카메라 프레임으로 두 엔진의 전체 코스트맵 출력을 비교해야 합니다.

## 9. 재현 명령

```bash
# state_dict 만 든 .pth (앱 TorchBackend 용)가 필요하면:
python -c "import torch; from pathlib import Path; from deploy.export_onnx import CheckpointLoader; sd,_=CheckpointLoader.load(Path('checkpoints/best_mIoU_iter_1600.pth')); torch.save(dict(sd),'/tmp/fastscnn_state_dict.pth')"
python -m eval.confidence_agreement \
    --models cpu_fp32=models/logits/fast_scnn_logits.onnx gpu_fp32=models/logits/fast_scnn_logits_fp32.engine \
             int8=models/calib_trt_adds/fast_scnn_qat_logits_int8.engine torch_cpu=/tmp/fastscnn_state_dict.pth \
    --pairs int8:gpu_fp32 --images data/images --gt data/labels_RGB --list data/splits/val.txt \
    --out results/confidence_agreement_1101
```
